# CAP signup verification

This service uses the official **capjs-core 0.1.6** and **cap-widget 0.1.58**, with proof-of-work and browser instrumentation. It replaces the native signup route's Discord verification requirement. The existing account service, password hashing, feature flags and signup cooldowns are retained. The original December form calls CAP programmatically; its historical markup/styles remain intact.

Use Node 22 or newer, run `npm ci` in this directory, then `npm start`. New configurations generated by `tools/configure_local.py` share a random secret between the website's private `Cap` settings and `.local/cap.json`. For an existing installation, set the website environment variables `Cap__Endpoint=http://127.0.0.1:3187/` and `Cap__Secret`, and set this service's `CAP_SECRET` to the same cryptographically random value (at least 32 bytes). Set `CAP_REDIS_URL` to the private Redis URL. Secrets belong in private configuration or environment files, never browser code.

The service binds to `127.0.0.1:3187` by default (`CAP_HOST`/`CAP_PORT` override this). Keep it private. The C# website exposes only `/captcha/challenge`, `/captcha/redeem` and four allowlisted assets; `/siteverify` is never publicly proxied. Both the widget and WASM are served locally. A bounded request body, per-client Redis rate limits and a generation concurrency limit apply. Missing configuration, unavailable Redis/CAP, invalid proofs and consumed tokens fail closed.

Redis stores used challenge nonces and short-lived verified tokens with atomic `SET NX` and `GETDEL`. Use persistent Redis with a no-eviction policy in production so restarting Redis cannot restore a still-valid redeemed challenge. Instrumentation is always enabled. Optional automation blocking can be enabled with `CAP_BLOCK_AUTOMATED_BROWSERS=true`; the default follows the official core's instrumentation behavior, rather than disabling checks for tests.

`tools/dev-database/verify-cap-signup.mjs` runs the real widget, C# signup, Redis and SQL engine. It checks account creation, password storage, session issuance, challenge/token replay rejection, outage handling and SQL restart persistence. See `docs/evidence/cap-signup/`. No test token, CAPTCHA success bypass or browser API fixture is built into the application.

Original December client resources and modern CAP are recorded separately. CAP is an intentional modern security integration, not a recovered 2018 component. Official references: [core](https://trycap.dev/guide/capjs-core), [widget](https://trycap.dev/guide/widget), [verification contract](https://trycap.dev/guide/). Dependencies retain their Apache-2.0 and other upstream license files through npm.
